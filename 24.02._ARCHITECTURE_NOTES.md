## Hot Path Analyse

### Rendering / Scrolling (SwiftUI)
**Zielbild:** Keine teuren Aggregationen/Sorts im `body`, keine DB/Cloud-Fetches im Render-Pfad, möglichst wenige invalidations.

Beobachtungen (konkret aus Code):
- `filmfreaks/Content/ContentView.swift`
  - **Gute Maßnahme:** Derived Movie-Listen werden außerhalb des Render-Pfads berechnet (`@StateObject ContentMovieItemsModel`), siehe `filmfreaks/Content/ContentMovieItemsModel.swift`.
  - **Gute Maßnahme:** Activity-Preview wird außerhalb des Render-Pfads gebaut (`ContentActivityPreviewModel`), siehe `filmfreaks/Content/ContentActivityPreviewModel.swift`.
  - **Hotspot-Risiko:** Viele `.onChange(...)` Trigger im Root können bei schneller Interaktion (Search/Filter/Mode) zu häufigen Updates führen. Grund: **exzessive View invalidation** durch viele State-Inputs. (File: `filmfreaks/Content/ContentView.swift`)
- `filmfreaks/MovieSearch/MovieSearchView.swift`
  - `@State searchTask/paginationTask` + Token-Schutz ist vorhanden (out-of-order).
  - **Hotspot-Risiko:** viele State-Variablen + results-Liste → bei großen Resultsets kann Pagination+List-Rendering teuer werden. Grund: **Scroll/Render pressure** (List cell complexity). (File: `filmfreaks/MovieSearch/MovieSearchView.swift`)
- `filmfreaks/MovieDetail/MovieDetailView+Lifecycle.swift`
  - `handleOnAppear()` startet `Task { await loadDetails() }` wenn `tmdbId != nil`.
  - **Hotspot:** **unbounded Task** ohne explizite Cancellation/Guard (außer evtl. innerhalb `loadDetails()` — Status **UNKNOWN**). Risiko: mehrfaches `onAppear` kann parallele Requests/State-Writes erzeugen. (File: `filmfreaks/MovieDetail/MovieDetailView+Lifecycle.swift`)
- `filmfreaks/Stats/StatsViewModel.swift`
  - Snapshot wird via `DispatchWorkItem` auf `DispatchQueue.global(qos: .userInitiated)` berechnet.
  - **Gute Maßnahme:** Work wird off-main berechnet, MainActor setzt nur das fertige Snapshot-DTO. (Files: `filmfreaks/Stats/StatsViewModel.swift`, `filmfreaks/Stats/StatsSnapshotBuilder.swift`)

### Sync / Storage (CloudKit + Disk)
**Zielbild:** inkrementelle Fetches (ZoneChanges), idempotente Writes, klare Invalidations, keine O(n²) Merges auf MainActor.

Beobachtungen (konkret):
- App-Resume Refresh-Kaskade:
  - `filmfreaks/filmfreaksApp.swift` → `.onChange(scenePhase == .active)` → `AppRefreshCoordinator.triggerRefresh(...)`
  - **Gute Maßnahme:** Coalescing + „max 1 in-flight, 1 rerun“ in `filmfreaks/AppRefreshCoordinator.swift`.
  - **Hotspot-Risiko:** Refresh-Action läuft auf **MainActor** und awaited mehrere Stores sequenziell; wenn Merge/Apply ebenfalls MainActor-heavy ist, entstehen UI-Stalls. (Files: `filmfreaks/filmfreaksApp.swift`, `filmfreaks/AppRefreshCoordinator.swift`)
- Movie Cloud Pull/Merge:
  - `MovieStore.loadFromCloud()` (`filmfreaks/MovieStore/MovieStore+CloudSync.swift`)
  - **Hotspot:** Apply von `changes.changed` nutzt wiederholt `watched.removeAll { $0.id == id }` / `backlog.removeAll ...` innerhalb einer Schleife.
    - Grund: **heavy sort/filter + O(n*m) removal** auf MainActor bei vielen Items/Changes.
    - Hebel: Index/Dictionaries (siehe Refactor Map).
- CloudKit Routing Guard:
  - `filmfreaks/CloudKitRouting.swift` verhindert Public-Fallback bei UUID-like groupIds ohne GroupContext.
  - **Hotspot-Risiko:** Wenn GroupContext noch nicht geladen/persistiert ist, schlagen Reads/Writes ab und Sync wird verschoben. UX kann „nichts passiert“ wirken, wenn kein Toast/Log vorhanden ist. Status **UNKNOWN** je nach Call-Sites.
- Inkrementelle ZoneChanges:
  - `filmfreaks/CloudKitZoneChanges.swift` + `filmfreaks/CloudKitZoneChangeTokenStore.swift`
  - **Risiko:** Token Korruption → discarding token ist implementiert (removes key), danach Full-Fetch. Edge case: „plötzlich viele Records“. (File: `filmfreaks/CloudKitZoneChangeTokenStore.swift`)
- Disk Persistenz:
  - `filmfreaks/PersistenceManager.swift` (debounced writes, migration).
  - **Risiko:** JSON Encode/Decode großer Arrays kann UI belasten, falls nicht sauber vom MainActor ferngehalten (Write-Scheduling ist da; genaue Threading ist **UNKNOWN**, siehe `scheduleWrite` Implementierung).

### Concurrency (MainActor, Task lifetimes, cancellation)
Beobachtete Patterns:
- **Coalescing + Cancellation**:
  - `filmfreaks/AppRefreshCoordinator.swift` (scheduledTask + inFlightTask)
  - `filmfreaks/MovieCloudSyncCoordinator.swift` (scheduledFlush Task, debounced)
  - `filmfreaks/MovieSearch/MovieSearchView.swift` (searchTask/paginationTask + tokens)
- **Generation Guards (Out-of-order)**
  - Stats Snapshot Build: `buildGeneration` + `DispatchWorkItem` + MainActor apply (`filmfreaks/Stats/StatsViewModel.swift`)
- **Risiko-Stellen**
  - Unscoped `Task {}` in View-Lifecycle ohne Cancellation (konkret: `filmfreaks/MovieDetail/MovieDetailView+Lifecycle.swift`).
  - MainActor „big merges“ nach await: Cloud fetch async → apply/merge sync auf MainActor (konkret: `filmfreaks/MovieStore/MovieStore+CloudSync.swift`).

### Cache-/Index-Ideen (mit Invalidations)
- Movie Cloud Merge Index:
  - Baue `Dictionary<UUID, Movie>` oder `Dictionary<UUID, Int>` Index für watched/backlog, apply delta in O(n + changes).
  - Invalidation: pro refresh/loadFromCloud call.
  - Betroffene Dateien: `filmfreaks/MovieStore/MovieStore+CloudSync.swift`
- Activity Preview Cache:
  - Bereits vorhanden via `ContentActivityPreviewModel`.
  - Option: `MovieStore.activityEvents(...)` intern mit revisions (moviesRevision/backlogRevision) cachen, falls Preview öfter verwendet wird. Betroffene Dateien: `filmfreaks/MovieStore/MovieStore+Activity.swift`, `filmfreaks/Content/ContentActivityPreviewModel.swift`

### Vereinheitlichungen (Patterns, DI, Stores)
- CloudKit Schema zentralisieren:
  - aktuell Keys/RecordTypes verteilt (MovieStore/RatingStore/GoalStore/MovieNightStore).
  - Optional: pro Domäne `Schema` struct/enum konsistent (RatingStore macht’s schon).
- Routing & GroupContext:
  - Konsequent jede Cloud-Funktion: `(db, zoneID)` via `CloudKitRouting.route(...)`, und fehlenden GroupContext als klaren Error/Toast surfacen.
  - Betroffene Dateien: `filmfreaks/CloudKitRouting.swift`, `filmfreaks/CloudKitGroupStore/CloudKitGroupStore.swift`, Call-Sites in Stores.

## Risiken & Edge Cases
- **Datenverlust / Sync Overwrites**
  - Local-first merges: Cloud snapshot/changes werden in lokale Arrays gemerged; bei Race Conditions (gleichzeitig lokale Edits) Risiko, dass lokale Änderungen überschrieben werden. Status der Konfliktstrategie ist **UNKNOWN** (müsste pro Store geprüft werden).
  - Konkrete Pfade: `filmfreaks/MovieStore/MovieStore+CloudSync.swift`, `filmfreaks/MovieNights/MovieNightStore+CloudFlush.swift`
- **GroupContext Not Ready**
  - UUID-like groupIds werfen/returnen früh → writes werden queued oder nicht ausgeführt. UX/Telemetry hier wichtig. (Files: `filmfreaks/CloudKitRouting.swift`, `filmfreaks/MovieNights/MovieNightStore+CloudFlush.swift`)
- **CloudKit Indexing**
  - Queries nach `groupId` in Public DB erfordern Index; Dashboard Status **UNKNOWN**. (File: `filmfreaks/CloudKitMovieStore/CloudKitMovieStore+Routing.swift`)
- **Secrets in Repo**
  - `filmfreaks/Secrets.xcconfig` enthält echte Credentials → kompromittierbar. (File: `filmfreaks/Secrets.xcconfig`)
- **Push/Background Fetch**
  - `didReceiveRemoteNotification` startet async `Task` und ruft completion handler nach await.
  - Risiko: zu lange fetches → OS killed/penalized. Implementierungsdetails von `fetchAndLog` sind **UNKNOWN** (File: `filmfreaks/CloudKitShareAppDelegate.swift`, `filmfreaks/CloudKit/CloudKitActivityPushFetchCoordinator.swift`)

## First 3 Refactors I would do (P0)

### P0.1 — MovieStore Cloud Merge: O(n²) → O(n)
- **Ziel:** UI-Stalls beim Cloud Refresh vermeiden, Merge/Apply skalierbar machen.
- **Betroffene Dateien:**
  - `filmfreaks/MovieStore/MovieStore+CloudSync.swift` (apply/merge in `loadFromCloud()`)
- **Risiko:** Mittel (funktional, muss exakt gleiche Semantik behalten).
- **Erwarteter Nutzen:** spürbar flüssiger bei großen Libraries + vielen Cloud-Deltas; weniger MainActor contention.

### P0.2 — UserStore splitten (mechanisch)
- **Ziel:** Wartbarkeit/Navigation/Compile-Time verbessern; weniger Merge-Konflikte.
- **Betroffene Dateien:** `filmfreaks/UserStore.swift` → Split in `UserStore+Persistence.swift`, `UserStore+CloudSync.swift`, `UserStore+Selection.swift`.
- **Risiko:** Niedrig (mechanisch, keine Logikänderung).
- **Erwarteter Nutzen:** schnellere Iteration im Sync/Users-Bereich; klarere Verantwortlichkeiten.

### P0.3 — Secrets Handling härten (rotate + gitignore)
- **Ziel:** Credential-Leak vermeiden, Build reproduzierbar ohne Secret im Repo.
- **Betroffene Dateien:**
  - `filmfreaks/Secrets.xcconfig` (aktuell enthält echten `TMDB_API_KEY`)
  - `filmfreaks/Debug.xcconfig`, `filmfreaks/Release.xcconfig` (include)
  - optional: `.gitignore` (**UNKNOWN**, nicht im ZIP gesehen)
- **Risiko:** Niedrig–Mittel (Build-Konfig; Devs müssen Key lokal setzen).
- **Erwarteter Nutzen:** Security + saubere Repo-Hygiene; weniger „oops“ Risiken.
